2、功能模块详细设计（模块业务流程实现与对应github分支）
本章详细描述本阶段聚焦的两个模块——场景管理与配置模块（数据操作层）与 3D 可视化沙盒模块（前端展示）——的业务流程，以及二者如何串起「地理数据 → 数据库 → 数据操作层 → 前端展示」的端到端链路。物理引擎、数据分析、沙盒绘制、AI 应用模块不在本阶段展开。
2.1 模块职责与分工
2.2 场景管理与配置模块（数据操作层）
2.2.1 职责
场景参数、方案干预参数、场景及方案地理数据的校验与保存。
作为唯一数据权威源：所有模块的数据读写都经过它，前端不直连计算模块、也不直连数据库。
负责把「地理数据入库」这一链路起点标准化，为前端 3D 沙盒提供统一的初始化与渲染数据接口。
2.2.2 业务流程
场景与地理数据入库流程
指定地理数据（GeoJSON 边界 / DEM COG）。
场景管理校验数据格式与坐标系（统一 EPSG:4326）。
按类型分流入库：矢量 → 写入 PostGIS（scene.bbox / intervention.geom）；栅格 → 上传 MinIO，登记 URL 到 scene（terrain_url / imagery_url）。
登记场景元数据（center / default_camera / env_params）。
返回 sceneId，前端据此发起 3D 沙盒初始化。
场景查询与更新流程
前端调用 GET /api/scenes/{sceneId}。
场景管理从 PostGIS 读取场景 + 底图引用。
返回 center / bbox / terrainUrl / imageryUrl / defaultCamera。
前端 Cesium 初始化视图并加载底图。
2.3 3D 可视化沙盒模块（前端展示）
2.3.1 职责
承载三维地形与二维叠加，展示基线/方案的湿格与热图。
提供交互控制（本阶段聚焦：视图定位、图层切换、干预要素展示）。
2.3.2 技术实现要点（基于 CesiumJS）
引擎选型：采用 CesiumJS，利用其全球 3D 地形 + 影像加载能力，适配真实地理坐标（EPSG:4326），与 PostGIS 存储坐标系天然一致。
渲染-状态分离（遵循系统设计架构原则）：可视化渲染层只负责「画」，应用状态层负责数据（通过 Zustand 管理场景/方案/要素状态），UI 层负责交互。
2.3.3 业务流程：场景加载与要素展示
前端进入沙盒。
调用 GET /api/scenes/{sceneId} 获取场景元数据。
初始化 Cesium Viewer：设置 camera（defaultCamera）、加载 terrain（terrainUrl）、加载 imagery（imageryUrl）。
完成「地理数据 → 数据库 → 数据操作层 → 前端展示」链路。
2.4 端到端链路数据流总览
整条链路由四个层次串起，数据自上而下流动：
链路闭环的关键点：
单一数据权威源：前端不直连数据库，所有数据经场景管理模块统一读写，保证一致性与可控。
GeoJSON 全程直传：PostGIS 的 geometry 列 ↔ GeoJSON ↔ Cesium GeoJsonDataSource 三者格式对齐，中间无需坐标换算或格式转换，是链路最顺滑的一环。
坐标系统一：全链路 EPSG:4326，数据库、接口、前端渲染保持一致。
场景为入口锚点：前端一切渲染均以 scene 的地理字段（center / bbox / terrainUrl / imageryUrl）为起点，形成清晰的依赖方向。
2.5 对应 GitHub 分支约定
两条分支可并行开发，以「场景管理提供的 REST API 契约」为联调节点；建议先合并 feature/scene-management，再合并 feature/sandbox-3d-visualization 跑通端到端链路。
3、模块接口文档
本章聚焦场景管理与配置模块对外暴露的 REST API，以及 3D 可视化沙盒依赖的数据获取接口。物理引擎（simulate 的计算部分）、分析、AI 相关接口只保留占位，不在本阶段展开实现细节。
3.1 接口总览
3.2 场景管理接口（数据操作层）
3.2.1 新建场景
POST /api/scenes
请求体：
 {
 "name": "某流域沙盒",
 "center": { "type": "Point", "coordinates": [120.15, 30.28] },
 "bbox": {
 "type": "Polygon",
 "coordinates": [[[120.10, 30.22], [120.20, 30.22], [120.20, 30.34], [120.10, 30.34], [120.10, 30.22]]]
 },
 "terrainUrl": "s3://sandbox/terrain/dem_cog.tif",
 "imageryUrl": "https://tiles.example.com/imagery/{z}/{x}/{y}.png",
 "defaultCamera": { "height": 5000, "heading": 0, "pitch": -45 },
 "envParams": { "temperature": 25, "precipitation": 120 }
 }
响应 201：
 { "sceneId": "uuid", "name": "某流域沙盒", "createdAt": "..." }
3.2.2 获取场景详情（3D 沙盒初始化入口）
GET /api/scenes/{sceneId}
这是前端 3D 沙盒加载的第一个调用：拿到 center / bbox / terrainUrl / imageryUrl / defaultCamera，据此初始化 Cesium 视图并加载地形与影像。
响应 200：
 {
 "sceneId": "uuid",
 "name": "某流域沙盒",
 "center": { "type": "Point", "coordinates": [120.15, 30.28] },
 "bbox": { "type": "Polygon", "coordinates": [[[120.10, 30.22], [120.20, 30.34]]] },
 "terrainUrl": "s3://sandbox/terrain/dem_cog.tif",
 "imageryUrl": "https://tiles.example.com/imagery/{z}/{x}/{y}.png",
 "defaultCamera": { "height": 5000, "heading": 0, "pitch": -45 },
 "envParams": { "temperature": 25, "precipitation": 120 }
 }
3.2.3 更新场景
PUT /api/scenes/{sceneId}：请求体同「新建场景」的字段子集，用于更新地理区域或环境参数。响应 200 返回更新后的完整场景对象。
3.2.4 删除场景
DELETE /api/scenes/{sceneId}：级联删除其下方案与干预要素（见数据库设计的 ON DELETE CASCADE）。响应 204。
3.3 方案与干预要素接口
3.3.1 列出方案
GET /api/scenes/{sceneId}/plans
响应 200：
 {
 "plans": [
 { "planId": "uuid", "planType": "baseline", "label": "基线" },
 { "planId": "uuid", "planType": "comprehensive", "label": "方案A" }
 ]
 }
3.3.2 获取方案下的干预要素（前端渲染数据源）
GET /api/plans/{planId}/interventions
这是 3D 沙盒绘制干预要素的核心数据接口：返回标准 GeoJSON FeatureCollection，前端直接交给 Cesium 的 GeoJsonDataSource 渲染，无需二次转换。
响应 200：
 {
 "type": "FeatureCollection",
 "features": [
 {
 "type": "Feature",
 "properties": {
 "interventionType": "绿地",
 "style": { "color": "#2e7d32", "opacity": 0.6, "extrusionHeight": 20 }
 },
 "geometry": { "type": "Polygon", "coordinates": [[[...]]] }
 }
 ]
 }
3.3.3 创建 / 保存方案
POST /api/scenes/{sceneId}/plans：接收方案元数据（planType / label / params），可选携带初始干预要素 GeoJSON，服务端校验后写入 plan 与 intervention 表。
 {
 "planType": "custom",
 "label": "方案B",
 "params": {},
 "interventions": [
 {
 "geometry": { "type": "Polygon", "coordinates": [[[...]]] },
 "interventionType": "透水铺装",
 "params": { "permeability": 0.6 },
 "style": { "color": "#1976d2", "opacity": 0.7 }
 }
 ]
 }
响应 201 返回 planId。
3.3.4 二次编辑方案
PUT /api/plans/{planId}：更新方案元数据或干预要素。响应 200。
3.4 地理底图接口
GET /api/scenes/{sceneId}/terrain
将场景登记的 terrain / imagery 引用与 bbox 一并返回给前端，作为 Cesium terrain/imagery provider 的初始化参数。
响应 200：
 {
 "terrainUrl": "s3://sandbox/terrain/dem_cog.tif",
 "imageryUrl": "https://tiles.example.com/imagery/{z}/{x}/{y}.png",
 "bbox": { "type": "Polygon", "coordinates": [[[120.10, 30.22], [120.20, 30.34]]] }
 }
3.5 统一响应约定
成功：2xx，数据体直接返回业务对象或 GeoJSON。
参数校验失败：422，返回 FastAPI 默认格式的 detail 数组。
资源不存在：404，返回 { "detail": "scene not found" }。
统一错误结构：{ "error": { "code": "SCENE_NOT_FOUND", "message": "..." } }（可与 FastAPI 默认格式并存，约定对外一律用此结构）。
4、数据库设计
本章只覆盖与「地理数据 → 数据库 → 场景管理与配置 → 3D 可视化」链路直接相关的表结构。物理引擎、数据分析、沙盒绘制、AI 应用相关的表（模拟结果栅格、分析报告等）不在本章展开，仅保留其关联字段占位。
4.1 数据库与存储选型
说明：wet grid / heatmap 等模拟结果栅格同样走 MinIO + COG，但属于物理引擎产出，本章仅在建表时以关联字段形式预留，不展开其写入流程。
4.2 表结构设计（核心链路）
4.2.1 scene（场景）
场景是整条链路的数据锚点：一个场景绑定一块地理区域（bbox / 中心点 / 地理底图），并挂载若干方案。前端 3D 沙盒的初始视角与底图加载均以 scene 的地理字段为入口。
 CREATE TABLE scene (
 id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
 name TEXT NOT NULL,
 -- 地理区域：核心地理锚点，驱动 3D 沙盒初始定位与底图裁剪
 center GEOMETRY(Point, 4326) NOT NULL,
 bbox GEOMETRY(Polygon, 4326),
 -- 地理底图引用（DEM / 影像），存对象存储地址，前端按需拉取
 terrain_url TEXT, -- Cesium Terrain / DEM COG 地址
 imagery_url TEXT, -- 影像底图地址
 default_camera JSONB, -- {longitude, latitude, height, heading, pitch}
 env_params JSONB NOT NULL DEFAULT '{}', -- 环境参数（温度 / 降水等）
 created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
 updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
 );
 CREATE INDEX idx_scene_center ON scene USING GIST (center);
 CREATE INDEX idx_scene_bbox ON scene USING GIST (bbox);
4.2.2 plan（方案）
方案分基线（baseline）与各类干预方案。方案改变下垫面，进而影响后续模拟，是「场景 → 可视化」链路中承上启下的对象。
 CREATE TABLE plan (
 id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
 scene_id UUID NOT NULL REFERENCES scene(id) ON DELETE CASCADE,
 plan_type TEXT NOT NULL DEFAULT 'custom'
 CHECK (plan_type IN ('baseline','economic','environmental','comprehensive','custom')),
 label TEXT, -- "基线" / "方案A" / "方案B"
 source TEXT NOT NULL DEFAULT 'manual'
 CHECK (source IN ('manual','ai')),
 nl_instruction TEXT, -- 若为 AI 生成，记录原始自然语言指令
 params JSONB NOT NULL DEFAULT '{}', -- 方案级参数卡
 created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
 updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
 );
 CREATE INDEX idx_plan_scene ON plan (scene_id);
4.2.3 intervention（干预要素）
统一要素模型：用户绘制与 AI 方案落地共用同一套「归一化 → 校验 → 3D 渲染」管线。几何用 GeoJSON 存入 PostGIS geometry 列，是「数据库 → 前端 3D 展示」最核心的一张表。
 CREATE TABLE intervention (
 id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
 plan_id UUID NOT NULL REFERENCES plan(id) ON DELETE CASCADE,
 geometry_type TEXT NOT NULL
 CHECK (geometry_type IN ('Point','LineString','Polygon')),
 geom GEOMETRY NOT NULL, -- 标准 GeoJSON 几何，SRID 4326
 intervention_type TEXT NOT NULL, -- "透水铺装" | "绿地" | "蓄水池" | "道路" | ...
 source TEXT NOT NULL DEFAULT 'manual'
 CHECK (source IN ('manual','ai')),
 params JSONB NOT NULL DEFAULT '{}', -- {area, permeability, storageVolume, elevation, ...}
 style JSONB NOT NULL DEFAULT '{}', -- {color, opacity, extrusionHeight}
 status TEXT NOT NULL DEFAULT 'draft'
 CHECK (status IN ('draft','validated')),
 created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
 updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
 );
 CREATE INDEX idx_intervention_plan ON intervention (plan_id);
 CREATE INDEX idx_intervention_geom ON intervention USING GIST (geom);
4.3 地理数据的入库方式（链路起点）
由于本阶段地理数据来源尚未最终确定，这里给出两种可落地的入库通道，二者都以「写入 PostGIS + 元数据登记到 scene」为终点，前端 3D 沙盒统一从 scene 读取入口。
通道 A：矢量数据（GeoJSON / Shapefile）→ PostGIS
流程：GeoJSON / Shapefile → 经 ogr2ogr 或前端上传 → 写入 PostGIS（intervention.geom / scene.bbox）→ ST_Transform 归一化到 EPSG:4326 → 登记到 scene → 场景管理 API 下发 → Cesium 渲染。
命令行示例（GeoJSON 导入为场景边界）：
 ogr2ogr -f "PostgreSQL" PG:"host=localhost dbname=sandbox user=postgres" \
 -nln scene_geom -nlt POLYGON -s_srs EPSG:4326 -t_srs EPSG:4326 \
 region.geojson
通道 B：栅格数据（DEM / 影像）→ MinIO + 元数据登记
流程：DEM / 影像（GeoTIFF）→ gdal_translate 转为 COG → 上传 MinIO（登记 terrain_url / imagery_url）→ 在 scene 表登记 URL + bbox → 场景管理 API 下发 → Cesium terrain/imagery provider 加载。
转 COG 并上传示例：
 gdal_translate -of COG input_dem.tif output_dem_cog.tif
 mc cp output_dem_cog.tif myminio/sandbox/terrain/
占位约定：在数据来源敲定前，代码中以 terrain_url / imagery_url 字段为唯一入口，前端不关心底图文件具体来源，实现时可先用一张示例 GeoJSON 边界 + 在线 Cesium 影像底图占位跑通链路。
4.4 链路相关的关键说明
空间索引：scene、intervention 的几何列都建 GIST 索引，保证「按区域查询方案/要素」的空间过滤性能。
几何坐标系：统一使用 EPSG:4326（经纬度），与 GeoJSON、Cesium 默认坐标系一致，避免前端换算。
删除级联：scene → plan → intervention 采用 ON DELETE CASCADE，删除场景时联动清理其方案与要素，保证数据一致性。
JSONB 承载异构参数：方案参数卡与干预要素参数用 JSONB，适配不同干预类型（透水铺装 / 绿地 / 蓄水池等）的差异化字段，无需为每种类型单独建表。
